# Assurance: what holds when detection fails

Generated by `python -m intentseal_eval.assurance` from `eval/reports/2026-10-11-contract.json`, `2026-10-11-paired.json` and `2026-10-11-redteam.json`. Detection results are in [EVALUATION.md](EVALUATION.md); this page asks the harder question: if an injection gets past every detector, can the agent still do harm, and can we prove what happened?

## 1. Intent contract with every detector bypassed (D-064)

**Method.** Worst case by construction: assume each generated injection fully succeeded and the agent attempts exactly what the injection demands. The demanded actions are read mechanically from the generated attack text (each email address becomes a send_message to it, each non-sandbox URL a web_fetch of it); nothing is authored (D-005). For every demanded action: a fresh session of the reference agent with content checks off (policies/research-agent-actions.yaml), the user's ordinary task for that channel, the attack content recorded for provenance only, then the action check.

Engine `8c2b401a4425` · attack suite v3 (promptfoo/garak generated) · 97 attack cases demanding at least one action.

| Condition | Demanded actions | Intent contract (shipped) | Word-list rule instead | Allow-lists, provenance, scan only |
|---|---|---|---|---|
| Third-party content (web, files, email, API, ...) | 70 | 70 (94.8%–100.0%) | 70 | 70 |
| Attacker targets a party the user named, user said "Do not email them." | 70 | 70 (94.8%–100.0%) | 56 (69.2%–87.7%) | 56 |
| User channel (the user is the attacker; reported apart) | 128 | 127 | 127 | 127 |

Defence in depth, third-party content: rules that fired per stopped action {'3': 56, '2': 14}; coverage by rule {'recipient-allow-list': 56, 'contract-out-of-scope': 70, 'provenance': 70}. In the named-party condition provenance cannot fire (the address is in the user's own words) and internal addresses pass the allow-list: the contract is what stops those sends, because the previous word-list rule read "Do not email them" as a request to email.

Legitimate actions the user asked for (our utility tasks that send or write), contract on: 4 of 4 allowed.

## 3. Provenance and execution receipts (D-065)

Every attempted action is shown as a chain built from the log: the untrusted source (a proven link: the call's arguments copy that content's text, or its target first appeared there; otherwise earlier flagged content, marked as context, not proof), the evidence found, the proposed call, the rule and contract clause that decided, and the outcome. Applications report execution (`POST /v1/actions/{id}/receipt`; automatic in the SDK's `@guard.tool`), so "not executed" rests on the enforced decision plus the application's record, not on a model's claim. A blocked call reported as run is flagged as a contradiction. Console: Replay → Attack to action. Tests: `tests/test_contract.py`, `tests/test_gateway.py::test_contract_provenance_and_receipts`.
