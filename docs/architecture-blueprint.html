Agent Security Gateway

A security layer that sits around any AI agent: it inspects everything the agent reads, checks everything the agent tries to do, and records every decision so a security team can replay it. This page designs each of the five parts on its own, then shows how they become one system.

The problem, in users' words

Real painWhat the design must do
"Our prompt filter was watching the user input field, not the document upload."Inspect every channel the agent reads
"If the scanner flags these, developers will disable it within a day."Low false alarms; monitor mode before enforcing
"LLM-provided kwargs can still override partial_params."Check every tool call; pin trusted fields
"On audit, 'we log tool calls' didn't survive contact."Record every decision; replay whole sessions
"Users approve 93% of permission prompts."Ask humans rarely, with a readable reason

Proposed solution: one security layer, shipped as an engine with four ways in, that catches what can be caught, limits what a hijacked agent can do, and proves what happened.

Job

  • Turn any content into a decision with a reason
  • Turn any proposed tool call into allow / block / rewritten arguments
  • Keep per-session risk and log every decision

Interface (Python)

engine.inspect(content, source,
               agent_id, session_id)
  → InspectResult(decision,
      cleaned_content, findings[])

engine.check_action(tool, args,
               agent_id, session_id)
  → ActionResult(decision,
      args, reason)

Data it owns

  • Policies per agent: task, allowed tools, pinned fields, sensitive patterns, thresholds, mode
  • Session risk state
  • Decision events (source, span, labels, tier, reason, action)

Failure behaviour

  • AI tier slow or down → rules only, result marked degraded
  • Per-tier time budget; never waits forever
  • High-risk content is never passed silently

Protects against

  • All 9 hackathon attack types (labelled on every finding)
  • Unwatched channels, reworded attacks, false alarms

Scope

  • MVP text, md, html, pdf, docx, email, json, code
  • MVP rules + 1–2 local classifiers + LLM judge
  • Stretch images via OCR
  • Later full data-flow (taint) tracking

Job

  • Wrap content loaders and tools with the fewest code changes
  • Supply trusted context (user, account) so pinned fields can't be changed by the model

Developer experience

guard = Guard(agent="research-agent",
              policy="policy.yaml",
              mode="monitor")

with guard.session(user_id=uid):
    doc = guard.inspect(raw, source="upload")

@guard.tool(pinned={"customer_id": ctx.id})
def query_db(customer_id, query): ...

Modes

  • Embedded: engine runs inside the agent process (no network hop)
  • Remote: calls the Gateway API (shared policies and logs across services)
  • Monitor / Enforce: log only, or apply decisions

Failure behaviour

  • Per tool: fail closed for tools that write or send, fail open (logged) for read-only tools, set in policy
  • Remote API unreachable → embedded rules fallback, marked degraded

Protects against

  • Indirect injection in files before extraction (hidden text, metadata)
  • Tool abuse, credential theft, secret extraction at the tool boundary

Scope

  • MVP plain Python + LangGraph/LangChain tool wrapper
  • Later other frameworks, JS/TS SDK

Job

  • Expose inspect and action-check over HTTP with a stable JSON contract
  • Serve sessions, decisions, policies and scorecards to the Console

Data it owns

  • Projects and API keys
  • Reads and writes the shared event store and policies

Failure behaviour

  • Every response carries degraded: true/false
  • Timeouts per request; health endpoint for the host
  • Rate limits protect free-tier model quotas

Scope

  • MVP endpoints above, API-key auth, SQLite
  • Later Postgres, multi-tenant orgs, SIEM export
Component 4 of 5

LLM Proxy

Zero-code protection. An agent changes only its model API address; the proxy inspects what goes to the model and what tool calls come back.

sequenceDiagram
  participant A as Agent (unchanged)
  participant P as LLM Proxy
  participant C as Core Engine
  participant M as Free upstream model
  A->>P: POST /proxy/v1/chat/completions
  P->>C: inspect user + tool messages
  C-->>P: cleaned messages
  P->>M: forward via LLM router
  M-->>P: reply with tool calls
  P->>C: check each tool call
  C-->>P: allow · block · pinned args
  P-->>A: safe reply (blocked calls → notice)

Job

  • Speak the OpenAI-compatible chat format most agents already use
  • Inspect inbound messages, check outbound tool calls, forward to a free provider

How a builder adopts it

base_url = "https://<gateway>/proxy/v1"
headers  = {"X-Agent-Id": "research-agent",
            "X-Session-Id": session_id}

Streaming

  • Tool-call pieces are held until complete, then checked, then released
  • Answers a real pain: a streaming path that skipped guardrails and leaked data

Honest limits

  • Sees text only: files were already extracted by the agent
  • Can't stop a tool the agent runs without asking the model
  • For both, use the SDK

Failure behaviour

  • Upstream provider fails → router tries the next free provider
  • Engine degraded → rules-only decisions, flagged in logs

Scope

  • MVP chat completions with tools, 2+ free providers
  • Later MCP traffic proxy, other API formats

Putting it together

One system: Agent Security Gateway

Four ways in, one engine, one event store. Numbers follow a single protected request.

  1. A user asks the research agent to summarise an uploaded report.
  2. The SDK receives the raw file before the agent reads it.
  3. The engine extracts everything the model would see, normalises it and runs the fast checks.
  4. Only if something looks suspicious, a free model is asked for a second opinion.
  5. The rules decide: the malicious span is quarantined and the rest goes to the agent, marked as untrusted data.
  6. The model proposes a tool call, for example sending a message.
  7. The engine checks it against the agent's task, pins trusted fields and scans for secrets.
  8. Only an allowed call reaches the tool.
  9. Every step is logged; the reviewer replays it in the Console.
